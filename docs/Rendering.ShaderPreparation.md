# Shader preparation and submission contract

Status: agreed lifecycle translated into an implementation contract; runtime migration has not started. Typed-facade generation, abstract enforcement, preparation-failure handling and adapter boundaries below are implementation decisions resolving the checklist, not claims about existing runtime behavior.
Governing checklist: [Rendering.ShaderPreparation.todo](Rendering.ShaderPreparation.todo), first task.
Current-source migration inventory: [Rendering.ShaderPreparation.Inventory.md](Rendering.ShaderPreparation.Inventory.md).

## Public API and ownership

Each runtime shader owner exposes `public void Prepare(Action<ConcreteShader> configure)` and the existing `Use`, `TryUse`, and scope entry points. The callback receives the concrete type, so callers can assign its actual parameters without casts. `Prepare` returns no readiness result and never activates, uploads, compiles, or links a program. Existing `EnsureReady` and preload operations continue to prepare executable generations; they are distinct from editing draw inputs.

Use a generated concrete `Prepare` facade, emitted for runtime shader owners by the existing shader generator, delegating to one lifecycle implementation. Keep the non-generic `GpuProgram` inheritance and existing layout APIs. The facade is a required typed API adapter, not a new copy of lifecycle logic. Detect runtime owners by their base type, including fixture owners without ShaderProgram attributes; do not generate this API on static contract/catalog declarations. Hand-authored runtime compute owners become partial owners under the compute submission base described below.

`GpuProgram` declares `protected abstract void Submit()`. Each concrete shader must override it, even if its explicitly documented resource contract is empty. A generator diagnostic enforces an override declared on the concrete owner (inheriting another concrete shader's Submit is insufficient); the abstract base gives compiler enforcement for direct omissions. Abstract shader bases do not provide an empty catch-all override. The activation template calls a protected virtual shared-input hook before the concrete `Submit`; `LumOnShaderProgram` owns shared frame/world-probe resources in that hook. Further shared bases chain their shared hooks. Thus common inputs cannot be forgotten by a concrete Submit implementation, and concrete submission remains mandatory. Generated resource helpers support an authored Submit; they never silently satisfy the abstract contract.

Setters retain CPU state. CPU UBOs own packed bytes and dirty tracking; shader instances own retained resource references and ordinary uniform values. Existing resource owners retain allocation/disposal responsibility. Copy array/span-backed parameter values into shader-owned storage when assigned: later mutation of the caller's array must not silently change prepared values. Store references for GPU resources, including authored texture-ID target/sampler policy; validate their current lifetime at submission. Reference retention is not ownership transfer or a GPU-resource lifetime extension.

## Persistent edits and failure semantics

- Construction establishes defaults. No successful Prepare, Use, Submit, or program reload resets unassigned fields. Multiple Prepare calls accumulate edits. Use without a preceding Prepare is valid when defaults/retained resources satisfy the current contract.
- Prepare runs synchronously on the shader's owning render thread. Runtime preparation/submission is not a concurrent editing API. Reject null callbacks before editing. Nested Prepare on the same owner joins the outer scope; only its outermost successful exit completes preparation.
- Runtime edits are in-place, not transactional. If any nested preparation fails, propagate the exception and mark the owner as having incomplete preparation, even if an outer callback catches it. Earlier assignments remain stored. Reject Use/TryUse submission until a later successful outer Prepare repairs/accepts that retained state; do not roll back bytes or publish a partial update automatically.
- Use, TryUse, UseScope, dispatch, explicit executable preparation, and preload of that owner are forbidden while its preparation scope is open. Reject before any GPU side effect. Editing another owner is allowed, but cannot cause submission of the owner under preparation.
- Ordinary runtime input assignments belong inside Prepare. Defaults in constructors, narrowly scoped internal initialization, and the engine adapters below are the allowed outside-scope writes. They still stage CPU data only. Development checks diagnose other out-of-scope writes; submission during preparation and incomplete-preparation rejection are release invariants. Owned UBO access must carry the owner edit guard so exposing a parameter object cannot bypass it. Standalone CpuUniformBuffer packing remains usable without a shader owner.
- Preserve existing ConfigureOptions/SetShaderOptions validation and atomic publication. Prepare wraps its callback in the owner's existing option-edit transaction where supported; generated option setters join that transaction. An exception discards option edits through that existing mechanism while runtime values remain in-place and the owner becomes incomplete. Existing option getters continue reading the last published snapshot. ConfigureOptions/SetDefines and global option configuration remain valid outside Prepare as CPU-only configuration APIs; they do not complete a failed runtime preparation. No extra runtime-state rollback is introduced.

## Activation and submission

Every explicit Use performs: reject incomplete/open preparation, EnsureReady for the latest published options, activate the installed program, update the program-state cache, validate required inputs for that generation, submit shared inputs, then concrete Submit. Repeated Use on an already-active shader still submits. Each owned UBO is published at most once during one successful Use. Submit binds retained textures, samplers, images, UBOs, SSBO ranges and ordinary uniforms against current interface metadata. Required missing/invalid inputs fail; optional or optimized-out inputs follow the declared contract. An optional unassigned input uses its declared fallback/unbound policy rather than inheriting an unrelated previous binding.

Submission may fail after some GL state changes; GPU state is not transactional. Use throws, TryUse returns false, and no subsequent draw is permitted. Clear the failed activation/current-owner state and preserve CPU inputs for retry. UBO dirty consumption follows successful publication; retry must bind/upload what is required regardless of clean CPU bytes. Do not introduce same-frame allocation caching here.

UseScope invokes the same submission path even for same-program nesting. Scope exit restores the previous VGE owner's current prepared state through its submission path, not just its program ID; it does not roll back CPU edits made inside the scope. A restoration failure must fail closed and surface to the caller rather than authorize an outer draw. For a non-VGE previous owner, preserve the existing engine activation convention: its caller owns restoring its resources before drawing. Do not claim arbitrary foreign GL state restoration. Centralize interface/base-class activation routing so engine IShaderProgram.Use cannot bypass Submit. Do not clear persistent CPU state when an engine reload disposes the old executable; terminal owner retirement still rejects future use.

For raw uniforms and generated resources, keep descriptor/slot/layout policy in the existing contract system. Generated setters store values and edit-state metadata; generated submission helpers apply those values only from Submit. Preserve explicit zero/null assignments and default behavior. Compile-time options remain in ShaderSettings, not in UBOs. Structural options must be published before EnsureReady selects the executable.

## Compute and engine boundaries

Introduce a runtime compute shader submission base that composes GpuComputePipeline and exposes the same preparation/submission lifecycle. Keep GpuComputePipeline as the executable/lifetime owner; its low-level activation cannot know an arbitrary wrapper's prepared inputs. Each runtime compute owner implements Submit. Static declarations such as WorldProbeTraceShader and AtmosphereComputePrograms remain descriptors; their current dispatch owners supply the runtime state. Multi-program owners need one submission owner/state per executable rather than one ambiguous Submit for an entire batch.

Compute Dispatch convenience methods perform owner Use exactly once before dispatch; DispatchBound requires a successfully submitted, still-current owner with no subsequent input edits or intervening resource disturbance. Retain existing barrier ordering, counters, output clears, readbacks and command-buffer uploads as explicit execution operations; they are not persistent parameter setters. Low-level pipeline use remains limited to executable infrastructure and fixtures that explicitly provide their own resources. Migrate production direct pipeline users listed in the inventory to runtime submission owners.

Liquid engine callbacks are the justified outside-Prepare runtime-input adapter: engine IShaderProgram.Uniform/UniformMatrix calls stage origin, model-view and transparency into retained draw state. LiquidRenderer and LiquidDepthRenderer currently hand rendering to mesh-pool managers after ApplyInputs; callbacks can then change values between pool draws. A VGE-liquid-only pre-draw bridge must invoke owner Use after those callbacks and before the actual draw. The inspected vsapi MeshDataPool.RenderMesh(IRenderAPI) forwards to IRenderAPI.RenderMesh and is a candidate hook, not yet a verified full ordering proof. Reconcile it with installed engine manager/mini-dimension ordering and existing terrain hooks in migration tests before removing PublishDraw. If a callback path bypasses that bridge, it must get another explicit pre-draw bridge, not a silent setter upload exception.

Vanilla engine shaders patched by terrain, atmosphere and world-probe hooks are not GpuProgram subclasses. Their existing engine submission hooks remain explicit adapters; they must not be represented as migrated owned shaders. Inventory and test their interactions with shared bindings and scope restoration. No broad engine mutation is authorized by this design contract.

## Completion and verification boundary

The first checklist task is documentation and inventory only. Later tasks implement the chosen API, generation changes, adapters and checks. Existing authoring examples remain descriptions of the current runtime until migration updates them. Preserve executable preparation behavior documented in GPU.ShaderDemandLoading.md, especially terminal retirement versus engine reload and failed-option retry suppression.

Implementation validation must cover typed callback inference, generated owner discovery, required concrete Submit enforcement, shared submission ordering, persistent partial edits, copied array inputs, nested/failed preparation including swallowed exceptions, existing option rollback, forbidden activation in Prepare, interface activation, scope restoration, missing inputs, reload and ring rollover, plus liquid pre-draw ordering and compute barriers. Counts of uploads per Use demonstrate batching; they do not establish measured frame-time savings.
