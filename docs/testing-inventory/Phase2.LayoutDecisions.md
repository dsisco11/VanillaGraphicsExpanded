# Test ownership and layout decisions

This is the migration map for `../Testing.SuiteReorganization.todo`. It records intended ownership; source paths in the inventories identify the original files and remain stable as files move. The method-level owner and boundary decisions in `Phase1.MigrationRouting.csv` and support decisions in `Phase1.SupportRouting.csv` control individual placements except where a source-backed correction is recorded below and applied by the map generator. Recheck a source body when the recorded owner is uncertain or a file contains multiple owners. This file is a migration aid and is removed after the decisions and reconciliation are retained in permanent documentation.

## Directory and namespace convention

Keep the four test projects separate. In each project, use `<Level>/<Domain>/<OwnedBehavior>Tests.cs`, where `<Level>` is `Unit`, `Component`, or `Integration` and `<Domain>` is the smallest stable production responsibility (for example `Atmosphere`, `Rendering/Resources`, `LumOn/WorldProbes`, or `Spirv/Cache`). The matching namespace is `<ProjectRoot>.<Level>.<DomainSegments>`. Do not add `EndToEnd` without a complete representative deployed workflow witness. Directory names express boundary and subject; traits express purpose and execution environment. Retain existing `Category`, `Purpose`, skip, and collection attributes during moves even when a legacy category name disagrees with the new level.

Put case-owned fixtures with their domain and level under `Fixtures`; put a fixture used by several domains under the narrowest shared `<Level>/Support/<Capability>` area. Keep genuinely cross-level infrastructure under project-root `Support/<Capability>` with explicit lifetime/collection ownership. Keep test input assets beside their consuming boundary when possible, but preserve copied output paths and stable shader asset identities. `GPU` and `Profiling` can remain names of support or asset areas; they are not test levels. Avoid a catch-all `Helpers` destination for unrelated responsibilities.

Name a test file for the contract it owns, with `Tests` as the suffix; partial files use the same class stem plus a scenario suffix. Split at a contract or level boundary, keeping inherited partial declarations together where required. Consolidate only closely related methods with one clear owner. A generated-runtime test with controlled collaborators is a component test even when Roslyn compiles an assembly. A GPU numerical component remains a component; a native state or submission boundary belongs in integration. Configuration-dependent tests whose path differs between Debug and Release stay with the principal exercised boundary and record the conditional path in their scenario documentation.

## Source routing

The two Phase 1 routing CSVs are the exhaustive source-to-owner keys: `Phase1.MigrationRouting.csv` covers all 837 attributed test files and `Phase1.SupportRouting.csv` covers 272 support sources. `Phase2.MethodMoves.csv` maps each attributed method to an exact destination path, namespace, class, and target method name; `Phase2.SupportMoves.csv` maps each support file to its destination and lifetime cue. Regenerate both with `../../tools/TestSuiteInventory/Generate-LayoutMap.ps1` after a routing decision changes. Where several rows share a source file, split only if their recorded owners or levels differ. The 125 files with more than one recorded level and 70 with more than one proposed owner require a method-by-method split decision; a file can be in both sets. Keep an existing file in place until its coherent migration batch is ready. Do not use current `Unit`, `GPU`, `Profiling`, class names, or `Category=GpuIntegration` as the classifier.
